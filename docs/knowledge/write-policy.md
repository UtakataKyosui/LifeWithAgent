# Knowledge Write Policy

Agentが将来のTaskで再利用できる知識を判別し、記録・訂正・削除する基準を定義する。特定のAgent実装（Claude Code、Codexなど）の機能名やツール名には依存しない。保存先の実装は #28（Episodic Memory）、記録の失効判定は #31（Knowledge Freshness、`docs/knowledge/freshness.md`）で扱う。このドキュメントは判断基準と記録形式のみを定義する。

## 1. 保存対象の区分

保存対象は次の5種類に限る。いずれにも当てはまらない情報は保存しない。

| 区分 | 定義 |
|---|---|
| Decision | 複数の選択肢から1つを選んだ判断と、その理由 |
| Constraint | 作業を制約する外部条件（API仕様、権限、コスト、期限など） |
| Failure | 試みて失敗した方法と、失敗した原因 |
| Finding | 調査や実装を通じて判明した、コード外の事実 |
| Experiment Result | 比較・検証を行った結果と、その条件 |

## 2. 保存基準と除外基準

### 2.1 保存する基準

次のすべてを満たす情報だけを保存する。

- 将来の別Taskで再利用できる（今回のTask限りの内容ではない）
- 現在のSource Codeを読むだけでは分からない（判断の理由、外部制約、失敗の経緯など、コードに残らない情報を含む）
- 再取得のコストが、記録のコストより高い（問い合わせ、再現実験、ドキュメント横断調査などが必要）

### 2.2 除外する基準

次のいずれかに当てはまる情報は保存しない。

| 除外対象 | 理由 |
|---|---|
| 進行中のTaskの実況・作業ログ（「〜を実装中」「次に〜をやる」） | Task終了後に再利用価値がない |
| ファイルを読めば分かる実装詳細 | Source Codeが正であり、複製すると陳腐化する |
| コマンド一発で再取得できる事実（`ls`、`grep`、`git log`の結果など） | 再取得コストが記録コストより低い |
| 公式ドキュメントやライブラリの一般的な仕様の要約 | 出典を直接参照する方が正確で、追跡対象が増えるだけ |
| 単純な誤字修正やフォーマット変更 | 再利用価値がない |

## 3. 記録形式

1件のエントリは次のフィールドを持つ。自由記述の本文だけでなく、機械的に絞り込める構造化フィールドを必ず含める。

| フィールド | 必須 | 内容 |
|---|---|---|
| `type` | 必須 | Decision / Constraint / Failure / Finding / Experiment Result のいずれか |
| `summary` | 必須 | 内容を1〜2文で要約したもの |
| `source` | 必須 | 出典。Issue番号、PR番号、コミットハッシュ、ファイルパス、外部URLのいずれか。複数可 |
| `recorded_at` | 必須 | 記録した日付（`YYYY-MM-DD`） |
| `scope` | 必須 | 対象範囲（リポジトリ全体、特定モジュール、特定機能など） |
| `verification_status` | 必須 | `unverified` / `verified` / `stale` / `superseded` のいずれか |
| `superseded_by` | 状態依存 | `verification_status` が `superseded` のとき、後継エントリのIDまたは出典 |
| `freshness_ref` | 任意 | 失効判定の根拠。`docs/knowledge/freshness.md` の基準IDを参照する |

### 3.1 記録例

```yaml
type: Constraint
summary: 外部APIのレート制限は1分あたり100件で、超過時は429が返る。
source: "Issue #45, https://example.com/api-docs#rate-limit"
recorded_at: "2026-09-20"
scope: "外部連携モジュール（src/integrations/example-api）"
verification_status: verified
```

```yaml
type: Failure
summary: ライブラリAをビルド時変換に採用したが、対象ランタイムでの動的import非対応によりビルドが通らなかった。ライブラリBへ変更して解決した。
source: "PR #58"
recorded_at: "2026-09-22"
scope: "フロントエンドのビルド設定"
verification_status: verified
```

エントリは常に `recorded_at` 時点の事実として記録し、「現在もそうである」という主張は含めない。記録された知識が現在のSource Codeの事実と一致するかどうかは、利用時に `freshness_ref` と `docs/knowledge/freshness.md` の基準で確認する。この分離により、保存された記憶と現在のSource Codeの事実を区別できる。

## 4. 重複・訂正・失効・削除の扱い

| 事象 | 扱い |
|---|---|
| 重複 | 既存エントリと`type`・`scope`・内容が実質同一なら新規エントリを追加せず、既存エントリの`source`に追記する |
| 訂正 | 既存エントリの内容を直接書き換えない。新しいエントリを追加し、古いエントリの`verification_status`を`superseded`にして`superseded_by`で新エントリを指す |
| 失効 | `docs/knowledge/freshness.md`の基準で無効と判定されたら`verification_status`を`stale`にする。エントリ自体は削除しない |
| 削除 | 記録内容が事実として誤っていた場合、実験が再現不能と判明した場合、または重複の統合が完了した場合に限り削除する。単に古いという理由だけでは削除しない（`stale`にする） |

訂正・失効を上書きではなく状態遷移として扱うのは、どの判断がいつ変わったかを後から追えるようにするためである。

## 5. 保存対象・非対象の判定表

親Issue（#26, #32）の本文には保存対象・非対象の具体例の記載が無かったため、代表例を以下に設定した。

| 例 | 判定 | 理由 |
|---|---|---|
| 外部APIのレート制限が1分100件だと判明した | 保存する | Constraintであり、問い合わせないと再取得できない |
| 認証方式をJWTに決定し、理由も記録した | 保存する | Decisionであり、コードを読むだけでは理由が分からない |
| ライブラリAの採用を試みたが依存関係の衝突で失敗し、Bに変更した | 保存する | Failureであり、同じ失敗の再発を防ぐ再利用価値がある |
| モデルXとYの応答速度を比較し、Yが1.4倍速いと分かった | 保存する | Experiment Resultであり、再実験しないと再取得できない |
| 「今日はログイン画面の実装を終えた」という進捗メモ | 保存しない | 進行中Taskの作業ログであり、Task終了後に再利用価値がない |
| `src/`配下のディレクトリ構成 | 保存しない | `ls`や`Glob`で容易に再取得できる |
| 使用しているフレームワークの公式ドキュメントの要約 | 保存しない | 出典を直接参照する方が正確で、陳腐化のリスクだけが増える |
| 変数名のtypoを修正した | 保存しない | 再利用価値がない |
